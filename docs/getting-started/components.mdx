In Tardigrade, a component is the smallest unit of an actor's behavior.

More specifically, a component is a state machine that takes events as input and produces an output based on its current state. Its current state is derived as a pure function of an append only event log. This builds on ideas from [automata theory](https://en.wikipedia.org/wiki/Automata_theory) and [event sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

<ComponentOverviewDiagram />

The first few sections would go deeper into the underlying concepts. I would recommend fully going through them to build better intuitions. However, jump straight to [authoring components](#authoring-components) if you want to quickly get started.

Let's start with state machines.

## State machines
### A simple state machine

[State machines](https://en.wikipedia.org/wiki/Finite-state_machine) is a concept from computational mathematics. They describe a thing that can exist in a finite set of states, transitioning from one state to another in response to inputs. A traffic light is a simple example of a state machine.

At any given point, a traffic light can exist only in one of three possible states: green, yellow, red. And there are specific rules that define how it transitions from one state to another.

<TrafficLightDiagram />

A simple traffic light could have the following state transition rules:

1. Green, timer expired → Yellow
2. Yellow, timer expired → Red
3. Red, timer expired → Green

Mathematically, it could be described as:

<Math expression="\text{next state} = \delta(\text{current state},\ \text{input})" />

For a traffic light, one of the transition could be written as:

<Math expression="\text{yellow} = \delta(\text{green},\ \text{timer expired})" />

Here, δ (delta) is the transition function: it takes the current state and an input, then returns the next state. For our traffic light, giving it green and “timer expires” returns yellow.

### Agents as state machines

Just like traffic lights, we could also view agents as state machines. Take an example of a simple tool calling agent. It can exist in one of the following possible states: calling a model, calling a tool, settled.

<AgentStateMachineDiagram />

It has the following transition rules:

1. Settled, message received → Calling model
2. Calling model, tool called → Calling tool
3. Calling tool, tool returned → Calling model
4. Calling model, turn completed → Settled

Mathematically, it could be described as:

<Math expression="\text{Calling model} = \delta(\text{Settled},\ \text{message received})" />

If we can write the states and the transition rules between states, we can describe an agent as a state machine.

### A brief note on side effects

I described components as pure functions over the event log. However, as you may have noticed in the example above, the output of a component is "calling a model". This is a side effect involving I/O. How can it be pure?

The Haskell community addressed this with the [IO monad](https://www.haskell.org/tutorial/io.html), which represents I/O actions as values to compose and execute later. [Effect](https://effect.website/docs/v4/getting-started/the-effect-type) follows the same idea.

Each Tardigrade component produces transitions that describe actions as Effect values. The runtime executes those actions. The `Effect<Success, Error, Requirements>` type makes the result, expected errors, and required services explicit. Type the world!

<WorldEffectDiagram />

### State explosion!

A tool calling agent is relatively simple to describe as a state machine. As our agents get more complex, we'd soon realise that it isn't practically possible to keep up with the current state and the transition rules anymore. A situation frontend developers know well as [state explosion](https://statecharts.dev/state-machine-state-explosion.html). Consider the same tool calling agent with a budget. Its next action now depends on both its execution phase and whether its tool budget is available or exhausted.

<StateExplosionDiagram />

Add retries, permissions, and more tools, and the states and transitions soon multiply. How do we deal with this complexity?

<StateComplexityIllustration />

## Enter components

The beauty of state machines is that they can compose with one another.

Instead of viewing the agent or actor as a single state machine, we can compose it into multiple state machines. In Tardigrade, these units are called components. Each component is a state machine that responds to a particular event based on the current state.

<ComponentCompositionDiagram />

We can compose whole agents this way too. One agent can use another through a tool. The called agent runs its own state machines, and its answer returns to the calling agent as a tool result.

<AgentCompositionDiagram />

## The *state* in the state machine

If you've noticed, each component is at a particular state at any given point. To pause and resume an agent, we could simply take a snapshot of the individual component state at a given point and hydrate the components with it. However, this method is very lossy.

We know the final position of the agent but we lose information about how it got there. How do we retain the complete history of an agent?

<StateSnapshotDiagram />

### State as a projection of the event log

A state machine transitions to another state after receiving an event as an input. So we can store the entire history of an agent by storing every event in an append only log. The current state at any given point could then be derived using a projection over the log. This concept is called [event sourcing](https://martinfowler.com/eaaDev/EventSourcing.html).

Take an example of a ship that's delivering goods to islands. To track different aspects of the ship, one way would be to maintain a separate database for each aspect and updating its state as the ship moves across islands. This is the typical approach that loses the history of how we arrived at a particular state.

For example, we could keep three tables in the same database, each storing one aspect of the ship's current state:

When the ship delivers another 10 crates, we update cargo to 30 and deliveries to 70. If we only keep these latest values, we cannot reconstruct the earlier stops or individual deliveries from them.

With event sourcing, we would instead write events into a log as the ship moves across islands. For example, we can stamp an event called `PositionUpdated` recording location and time whenever the ship reaches an island. I can get the exact path of the ship by replaying the events, and I can get the state at specific points in the journey by folding the logs.

<ShipPositionDiagram />

The same log can yield location, distance, or elapsed time. Each projection is pure: the same events produce the same result.

### Agent state as projection

Each component derives its state from the same event log. Inference tracks messages and tool calls, budget tracks usage, and permission tracks requests and decisions. The same history yields three different states. Here, the turn has completed, the tool call has spent the last of the budget, and its permission has been cleared.

<AgentProjectionDiagram />

### Putting it together

Summing it all up, a component reads the event log, derives its current state, and describes what to do next as an Effect. The runtime executes that Effect and records its result as another event. That event becomes part of the history from which the component derives its next state.

<ComponentCycleDiagram />

## Supplying inputs to children

A parent can supply typed input constructors when building its children. The infer builder exposes `message`, the stable constructor also available as `agent.input.message` on the component returned by `infer`. It describes an agent turn without evaluating infer output. The alarm package chooses its response through `onFired`:

```ts
infer(({ message }) => [
  tools([
    alarm({
      onFired: alarm => message({ text: alarm.note }),
    }),
  ]),
  nativeOutput,
])
```

The same alarm package works inside `codeMode`. Its `set` method takes `{ wakeAt, note }`, where `wakeAt` is a Unix timestamp in milliseconds, and returns an alarm ID. Its `cancel` method takes `{ id }`. The host records requests in the log and arms the earliest outstanding wake.

Calling `message` constructs a request. When an alarm fires, its component binds that request to the recorded firing and proposes a transition. The runtime commits the message before inference starts the turn. Replaying the firing preserves its transition identity. The package recognizes the committed response through that identity, independently of the response event type.

Builder capabilities pass through wrappers such as budget and tools. Scopes allow binding in the declaring component, its descendants, and its direct parent. Unrelated subtrees cannot bind a captured capability unless it is explicitly re-exposed through a component's `input` field. Callbacks and event constructors must be pure because projection and replay may evaluate them repeatedly. Returning `undefined` from `onFired` proposes no response.

## Authoring components

Now that we've learnt the concepts, it's time to get our hands dirty. In this section we'll author a Tardigrade component from scratch. We'll build with a custom tool that lets a model search its own event log and those of its child agents.

### Initial state

`initial` defines the component's state before it has processed any events. Our search tool starts with no pending requests, so its initial state is an empty list.

```ts
initial: () => [],
```

### Updating state

`step` receives the current state, an event, and a `context` supplied by the runtime. It returns the next state. For our search tool, a `ToolCalled` event adds a pending search request. When that request completes, we remove it. Unrelated events leave the state unchanged.

The context links work to the event that caused it. We save it with each request, use `context.effect("search", ...)` to declare its search, and use `context.matches("search", event)` to recognize its completion and remove the right request.

```ts
step: (pending, event, context) => {
  if (
    event.type === "ToolCalled" &&
    event.name === "search_logs" &&
    typeof event.callId === "string"
  ) {
    return [...pending, {
      context,
      call: {
        callId: event.callId,
        name: event.name,
        arguments: event.arguments,
        ...(typeof event.turn === "string" ? { turn: event.turn } : {})
      }
    }]
  }

  const remaining = pending.filter(
    (request) => !request.context.matches("search", event)
  )
  return remaining.length === pending.length ? pending : remaining
},
```

`step` only updates state; the search itself is declared through `output`, which we'll define next.

### Output

`output` reads the current state and returns a `view` and `transitions`. The view shares information with other components. Transitions describe work the runtime can perform, either proposing events through an intent or running external work through an effect.

Our search tool exposes the number of pending requests and declares a search effect for each one.

```ts
output: (pending) => ({
  view: { pendingCalls: pending.length },
  transitions: pending.map(({ call, context }) =>
    context.effect("search", {
      input: call,
      act: (input, { signal }) => Effect.gen(function* () {
        const result = yield* searchLogs(input, signal)
        const at = yield* Clock.currentTimeMillis
        return { type: "ToolReturned", ...input, result, at }
      })
    })
  )
}),
```

Here, `searchLogs` is a function we supply to search the agent's own log and its child agents' logs. `output` declares the effect; the runtime runs `act` and records its `ToolReturned` event. That event flows back through `step`, which removes the completed request. With no pending requests, the component outputs no search effects.

#### Complete example

The pieces together, with `Clock` and `Effect` for the external action:

```ts expanded
import { Clock, Effect } from "effect"
import { component, type TransitionContext } from "tardie/core"

type Call = {
  callId: string
  name: string
  arguments: unknown
  turn?: string
}

type Pending = {
  call: Call
  context: TransitionContext
}

const searchTool = (
  searchLogs: (call: Call, signal: AbortSignal) => Effect.Effect<unknown>
) => component({
  name: "search_logs",
  initial: (): ReadonlyArray<Pending> => [],
  step: (pending, event, context) => {
    if (
      event.type === "ToolCalled" &&
      typeof event.callId === "string" &&
      event.name === "search_logs"
    ) {
      return [...pending, {
        context,
        call: {
          callId: event.callId,
          name: event.name,
          arguments: event.arguments,
          ...(typeof event.turn === "string" ? { turn: event.turn } : {})
        }
      }]
    }

    const remaining = pending.filter(
      (item) => !item.context.matches("search", event)
    )
    return remaining.length === pending.length ? pending : remaining
  },
  output: (pending) => ({
    view: { pendingCalls: pending.length },
    transitions: pending.map(({ call, context }) =>
      context.effect("search", {
        input: call,
        act: (input, { signal }) => Effect.gen(function* () {
          const result = yield* searchLogs(input, signal)
          const at = yield* Clock.currentTimeMillis
          return { type: "ToolReturned", ...input, result, at }
        })
      })
    )
  })
})
```

## Runtime dependencies

Declare runtime services in `dependencies`. The framework binds them once per initialization or restore and supplies them to `initial(children, data)` and `output(state, children, data)`. A restore obtains services from its supplied runtime context; checkpoints contain only the component's private state and child checkpoints.

Keep live services and executable implementations outside private state. Output can derive proposed work from durable facts and its dependency bindings. The inference component follows this contract: its state retains turn history and model-failure counts, while output receives `ModelLock` through its declared dependency. Equivalent replay and restored behavior require compatible dependency configuration. Changing that configuration can intentionally change derived output.

## Checkpoint state

A component can opt into the framework's checkpoint encoding contract with a synchronous Effect Schema and an explicit compatibility version:

```ts
const counter = component({
  name: "counter",
  checkpoint: {
    version: "1",
    schema: Schema.Struct({ count: Schema.Finite })
  },
  initial: () => ({ count: 0 }),
  step: (state, event) => event.type === "Tick"
    ? { count: state.count + 1 }
    : state,
  output: (state) => ({ view: state, transitions: [] })
})
```

The schema encodes private state as JSON and restores its runtime representation. Its round trip must preserve everything the reducer and output function need for future events. Change the version when the stored representation or reducer semantics become incompatible with existing checkpoints. Schema validation cannot detect a behavioral change in the reducer.

A parent declares a schema for its own state. The framework recursively checkpoints its children, preserves child admission positions and timestamps, and rebuilds handles and outputs on restore without calling initializers. Every child must support checkpointing. Child names, order, and versions must match the restored tree.

`composeComponents` opts in through `{ checkpoint: { version: "1" } }` in its options. Its private representation is managed by the framework. Change this version when its view algebra, interaction projection, or reconciliation behavior becomes incompatible. Compositions with a custom reconciler retain their event history in the checkpoint because reconciliation reads that history; checkpoint size can therefore grow with the log.

Checkpoint encoding and decoding are internal machine operations. The actor reconciler captures execution bookkeeping and the durable log watermark together. The Bun host can persist that checkpoint in the thread database and load it during recovery.


### Historical child state

A parent can retain a private child snapshot with `child.retain()` and read that snapshot through `child.at(snapshot)`. The reference exposes no child state. Different snapshots have identity equality, including when stored in persistent collections. A reference from another child is rejected.

A checkpointed parent that retains historical children declares `checkpoint` as a function of its child handles. The child's `snapshotSchema` encodes each retained reference through that child's own checkpoint contract and restores its state under the new runtime context. The parent schema can include these references alongside its other state. Retained snapshots can increase checkpoint size because their private state is encoded in addition to the current child state.

Tool routing retains data-only command offers for native and code tools. Each command names an implementation and compatibility version and includes its schema-validated parameters. `toolCommand({ name, version, schema, serve })` defines behavior outside component state; its `command(input)` method produces an offer's durable `command`. Pass the implementation through `toolComponent(child, { implementations: [implementation] })`. A restore requires compatible implementations for the saved commands. Native tools accept a `version` override; change it when their execution semantics change.

Offers with a custom `serve` callback retain a child snapshot using the state immediately before `ModelCalled`, or immediately before `ToolCalled` when there is no recorded offer. Offers without handlers retain routing facts. Pending calls use their accepted offers even after state changes or tool removal. Transition contexts are rebuilt from the call's originating event and position. `toolComponent(child, { checkpoint: { version: "1" } })` enables checkpoints when the child supports checkpointing.

Tool responses use data-only event records with the call's transition identity and invocation. The runtime supplies their `at` timestamp when committing them. Budget refusals retain these response records without retaining the responding child tree. Arbitrary custom response callbacks retain the historical-child path. A data-only response must contain JSON values; functions, service instances, accessors, and cycles are rejected.

Bookkeeping consumers use turn lifecycle facts without a trajectory or per-turn event arrays. Budget accumulates grants, initial-grant status, and phase, and removes refusal payloads once their completion is recorded. Message-method status and output repair retain the declarations and outcomes they query. Code execution drops settled dispatch bodies and returned package-call records while retaining identifiers for duplicate suppression and call ownership. Permissions retains first decisions and outstanding authority-call stages, drops those stages when the decision is recorded, and excludes unrelated execution events.

A tool component with registered implementations defaults to `history: "call"`: handlers receive the accepted thread and turn context plus events observed since that call. Custom `serve` callbacks default to `history: "turn"`, which also retains the preceding turn history. `toolComponent` accepts an explicit `history` override. The inference router uses call history; call-history routing rejects custom `serve` callbacks because they require the historical-output path. Checkpoints record the selected mode and reject a mode mismatch during restore.

Conversation and inference projections retain history that their APIs expose. Inference supplies a served trajectory to model execution and uses it for retrospective cost correction. Custom instruction callbacks and budget escalation can also require histories. Lifecycle outcomes, permission decisions, accepted-call facts, and transition identifiers can grow with the number of invocations: retries, late replies, and duplicate suppression still query them. These records have no arbitrary FIFO expiry.


### Actor recovery boundary

`createActorReconciler(runtime, { checkpoint: { actor, version, stream }, restore })` enables runtime checkpointing. Every transition projection and the optional control projection must supply a state codec. Component transition adapters carry their component codec through this boundary. Runtimes with complete-log cancellation callbacks are unsupported. Compiled actors support checkpointing when every component, method projection, and durable input validation projection declares a checkpoint. Method and validation projections use `{ version, schema }`, with the same JSON round-trip contract as component state. Complete-history method and validation adapters remain unsupported. Built-in agent components provide codecs when their children support checkpointing; custom components must declare their own state schemas.

After synchronization, `reconciler.checkpoint()` captures the published projection states, completed transition keys, tracing context, and log watermark together. It can capture blocked work as well as a resting actor. Events appended after that watermark belong to the recovery tail. A host must serialize drives of an activation and store the entire checkpoint atomically against the same immutable stream. Capture does not append to the log or write storage.

Recovery validates the envelope, identity, watermark, and projection codecs before publishing restored state. A compatible checkpoint skips prefix reduction and reads from its watermark. A rejected checkpoint falls back to full replay, with the reason exposed by `reconciler.recovery()`. Failure while reducing the tail remains an execution failure; a later drive retries from the published prefix.

The host supplies a stable stream identity that changes when a log is replaced. The actor version covers projection order, guards, key derivation, reducer behavior, and dependency configuration. Change it when those semantics become incompatible. Identity and schema checks do not authenticate checkpoint contents or detect arbitrary edits to a log prefix. Preserve the full event log for fallback recovery.


### Bun checkpoint storage

Pass `checkpoint: { version: "1", onRecovery: (thread, recovery) => { /* observe recovery */ } }` to `createBunHost` to enable persistence. The version identifies the compatible actor configuration returned by `actorFor`. Checkpointing is disabled when this option is absent; enabling it requires every actor served by that host to support checkpoints.

Each thread's SQLite database contains an `actor_checkpoint` row with a persistent stream identity and the latest complete checkpoint. After a successful drive, the host atomically replaces that row when the published watermark changes. A failed write leaves the previous checkpoint available and fails the drive. A subsequent drive or restart can retry from the retained checkpoint and durable log.

The host reports checkpoint acceptance or replay fallback through `onRecovery`. Malformed JSON, incompatible versions, invalid state, and watermarks beyond the log cause full replay. A fresh database receives a fresh stream identity. Keep the checkpoint and its event log together when copying a database.

Checkpoint recovery skips prefix reduction in the actor reconciler. Host directory repair, graph scheduling, and alarm discovery still read history, so this does not eliminate all startup log reads. Cloudflare checkpoint persistence remains separate work.
